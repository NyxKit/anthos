# Executive Summary
This codebase works, but it is carrying a lot of local decisions that have not been reconciled into a clean architecture. The strongest parts are the shared domain types and the fact that there is real test coverage around core flows, but the biggest pain themes are weak trust boundaries, manual persistence, and UI/service components that have grown into small ecosystems.

Future rot risk is high. The code feels partly intentional and partly stitched together by feature pressure: not a disaster, but definitely not a system that will stay pleasant if the team keeps adding features at this pace.

Top 3 priorities:
1. Fix the public trust boundary around ingestion and node-facing endpoints.
2. Lock down user-management authorization on the server.
3. Remove manual persistence and ID-generation footguns in the registry layer.

# Findings

### [Critical] Public mutation endpoints with no real trust boundary

**Category:**
Security

**Time horizon:**
Immediate

**Blast radius:**
Systemic

**What’s annoying:**
The server accepts telemetry, log writes, and node registration from unauthenticated callers, while `app.ts` enables blanket CORS. That means the system trusts whatever lands on the wire and then happily uses it to update state, write archives, and trigger automation.

**Why it matters later:**
Any client on the network can spoof telemetry, poison logs, and potentially trigger pump commands through automation evaluation. This is not just “a little too open”; it is the core control plane being reachable without a credible identity check.

**Evidence:**
`server/api/src/app.ts:24-33` uses `cors()` globally.
`server/api/src/controllers/IngestController.ts:29-69` accepts telemetry with only shape checks, then feeds it into registry, telemetry storage, log archival, and `AutomationEvaluator`.
`server/api/src/controllers/LogsController.ts:19-53` accepts arbitrary log entries with no auth.
`server/api/src/controllers/ProvisionController.ts:16-60` accepts node registration with only `hwId` and a pairing-window check.
`server/api/src/services/AutomationEvaluator.ts:24-89` can enqueue pump commands from the incoming payload.

**What’s really going on:**
The code treats HTTP input as if it were already a trusted device session. That is fine for a prototype, but it is not a production trust model.

**Suggested fix:**
Split public read APIs from device write APIs, require authenticated device identity for telemetry/logging/registration, and stop relying on body-supplied `hwId` as proof of origin. At minimum, add per-node signed requests or mTLS for device writes and tighten CORS to known app origins.

**Roast line:**
This control plane is currently running on “please be honest” as its authentication strategy.

### [High] User management authorization is too weak for the power it exposes

**Category:**
Security

**Time horizon:**
Immediate

**Blast radius:**
Systemic

**What’s annoying:**
Any authenticated user with `canPerformActions` can update or delete arbitrary users, including changing roles. The frontend hides some of this, but the server does not enforce the same rule.

**Why it matters later:**
This is role escalation waiting for one curious user or one forgotten API client. The frontend cannot be the thing preventing privilege abuse.

**Evidence:**
`server/api/src/services/AuthService.ts:54-69` defines `requireActionUser()` as allowing both `admin` and `user`.
`server/api/src/controllers/UserController.ts:160-205` uses `requireActionUser()` for `update` and `delete`, and `update()` accepts `role` changes at `lines 170-176`.
`server/api/src/controllers/UserController.ts:18-30` also uses `requireActionUser()` for listing users.
`server/api/src/controllers/UserController.ts:116-158` only uses `requireAdmin()` for create, which makes the inconsistency more obvious.

**What’s really going on:**
Authorization is being inferred from UI intent instead of enforced at the boundary. That works until the first non-UI client shows up, which is usually immediately.

**Suggested fix:**
Require admin for user-management endpoints that affect other accounts, keep `me` separate from admin CRUD, and explicitly block role changes from non-admin actors.

**Roast line:**
The server is letting regular users do admin work because the frontend promised to be nice about it.

### [High] Registry persistence is manual, leaky, and already dropping writes

**Category:**
Maintainability

**Time horizon:**
Immediate

**Blast radius:**
Cross-cutting

**What’s annoying:**
`NodeRegistryService` mutates the database in memory, but persistence is handled by callers. Some callers remember to save after every mutation, some only save on the happy path, and some mutate without any persistence at all.

**Why it matters later:**
This is how you get phantom state, disappearing reconnect data, and “why did this node forget its firmware?” bugs that only appear after a restart or crash.

**Evidence:**
`server/api/src/services/NodeRegistryService.ts:17-42` and `254-264` mutate hardware state directly.
`server/api/src/controllers/IngestController.ts:37-46` calls `upsertHardwareNode()` and only persists when the node is newly created; reconnecting nodes update `last_seen` in memory and then return.
`server/api/src/controllers/ProvisionController.ts:27-46` has the same pattern on reconnect: `upsertHardwareNode()` runs, but the early return skips `saveDb()`.

**What’s really going on:**
The service layer does not own its own durability. That means correctness depends on every caller remembering to flush the right way, which is a very expensive way to simulate invariants.

**Suggested fix:**
Make registry mutations durable inside the registry service itself, or wrap mutations in a transaction-and-save helper that cannot be skipped from the controller layer.

**Roast line:**
The registry has the memory of a goldfish and the commit discipline of a teenager.

### [High] Logical node IDs are generated with `MAX()+1`, which is a race condition dressed as a naming scheme

**Category:**
Scalability

**Time horizon:**
1–3 months

**Blast radius:**
Feature-level

**What’s annoying:**
New node IDs are derived from `SELECT MAX(...) + 1`. That is simple, readable, and wrong the moment two registrations happen close together.

**Why it matters later:**
Concurrent provisioning can produce duplicate IDs or failed inserts. The larger the install base gets, the more likely this turns into a support ticket with no obvious repro.

**Evidence:**
`server/api/src/services/NodeRegistryService.ts:63-85` calculates `nodeId` from the current max suffix and inserts without a transaction or retry loop.

**What’s really going on:**
This is a classic “it works on my laptop” sequence generator. It assumes registration is serialized forever, which is not a safe assumption.

**Suggested fix:**
Use a dedicated sequence/counter table, a transaction with retry, or another atomic ID allocator. Keep the human-readable `node-001` format, but stop deriving it from a non-atomic scan.

**Roast line:**
`MAX()+1` is not an ID strategy; it is a coincidence generator.

### [High] Telemetry is buffered in memory long enough to lose real data

**Category:**
Rot resistance

**Time horizon:**
1–3 months

**Blast radius:**
Systemic

**What’s annoying:**
Telemetry ingestion stores readings in `pendingReadings` and only flushes them every minute or on shutdown. Snapshots are written to the in-memory SQLite database immediately, but they are not durably persisted to disk until the periodic flush happens.

**Why it matters later:**
A crash, power loss, or process kill wipes up to a minute of readings and any recent snapshots. That means the system can be “working” while silently losing the data it exists to capture.

**Evidence:**
`server/api/src/services/TelemetryService.ts:273-323` appends readings to `pendingReadings` and flushes only when `timestamp - lastStoredAt >= STORE_INTERVAL_MS`.
`server/api/src/services/TelemetryService.ts:325-334` persists the database only when `saveDb()` runs.
`server/api/src/services/TelemetryService.ts:394-402` flushes pending reads only during close.

**What’s really going on:**
Durability is being traded for simplicity without a real backpressure or recovery story. That is fine until the process stops being immortal.

**Suggested fix:**
Persist more frequently, bound the queue, and define what happens when storage falls behind. If write amplification is the concern, make the batching explicit and observable instead of accidental.

**Roast line:**
This telemetry pipeline is one crash away from becoming a very expensive memory cache.

### [Medium] `NodeCardActions` is a god component, and the BLE provisioning composable leaks listeners

**Category:**
Maintainability

**Time horizon:**
3–6 months

**Blast radius:**
Feature-level

**What’s annoying:**
`NodeCardActions` handles pump control, power profile application, node editing, log-driven command completion, and modal state in one component. On the provisioning side, `useBleProvisioning` adds a notification listener every time `startNotify()` runs and never removes it.

**Why it matters later:**
This is the kind of code that makes small changes feel like operating on a live wire. The component works, but every new interaction adds another watcher, ref, or branch to an already crowded control flow.

**Evidence:**
`app/src/dashboard/components/NodeCardActions.vue:1-344` contains pump state, profile state, edit modal state, log correlation, and three separate command flows.
`app/src/composables/useBleProvisioning.ts:15-21` attaches a `window.addEventListener(...)` callback after BLE notify starts.
`app/src/composables/useBleProvisioning.ts:75-107` handles connection, provisioning status, and disconnect cleanup, but never unregisters listeners or resets them on retry.

**What’s really going on:**
The UI layer is carrying too much orchestration logic instead of pushing behavior into smaller, testable units. The BLE composable has the same smell: it solves the happy path and leaves the cleanup path for future regret.

**Suggested fix:**
Split node actions into dedicated composables or child components, and return an unsubscribe/cleanup function from BLE notification registration so retries do not stack duplicate listeners.

**Roast line:**
This component has collected responsibilities like Pokémon and now none of them get enough attention.

# Systemic Patterns
- Trust and persistence are both scattered across layers. Controllers validate, services mutate, callers remember to save, and the frontend mirrors parts of the same rules. That is why the codebase keeps producing “almost enforced” behavior.
- Client wrappers are thin enough to look clean, but they mostly move ceremony around instead of centralizing policy. The result is lots of code that feels organized without actually reducing risk.
- The frontend likes large orchestration components and local watcher state. That makes feature work fast early and expensive later.
- The test suite covers the sunny-day paths better than the failure modes. The scary stuff here is authorization, concurrency, cleanup, and durability, and those are not the places where the current tests spend their time.

# Fix Order
- Fix now: lock down telemetry/log/node write endpoints and user-management authorization. These are direct security and control-plane issues.
- Fix now: stop skipping `saveDb()` on registry reconnect paths. That is already causing silent data loss.
- Fix next: replace `MAX()+1` node ID allocation with an atomic allocator.
- Fix next: make telemetry persistence durable enough to survive crashes without losing a minute of data.
- Fix opportunistically: split `NodeCardActions`, clean up BLE listener lifecycle, and trim repeated validation glue.
- Monitor only: cosmetic CSS drift, small import/style inconsistencies, and other harmless snowflakes.

# What Not To Waste Time On
- Don’t rewrite the entire shared `Anthos` client just because it has many thin methods. The real problem is boundary trust, not the existence of a wrapper.
- Don’t chase minor style issues like the odd import indentation in `LogsView.vue` while the server is still trusting arbitrary input.
- Don’t over-abstract the UI primitives before the ownership and lifecycle problems are fixed.

# Final Verdict
This is a working codebase with a shaky spine: useful features, decent scaffolding, and too many places where correctness depends on someone remembering the unwritten rule. In a year, unchanged, it will feel slower to extend and more dangerous to trust. Clean up the boundaries and persistence model now, and it can become a coherent system instead of a pile of well-meaning feature islands.
