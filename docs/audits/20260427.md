# Executive Summary
This codebase is materially better than a stitched-together prototype, but it still has a few places where the system depends on manual discipline instead of enforced structure. The strongest traits are the now-cleaner backend ownership around persistence and the shared domain contracts, while the biggest pain themes are weak test coverage on the server, multi-step UI mutations pretending to be atomic, and lifecycle/caching logic that quietly outlives the screen that created it.

Future rot risk is moderate to high. The backend spine is more intentional than before, but the frontend still has pockets of global state and side effects that will get annoying fast when the app grows.

Top 3 priorities:
1. Put high-value backend flows under test, especially auth, registration, commands, and automation evaluation.
2. Make node editing and provisioning behave like coherent flows instead of a pile of independent side effects.
3. Put bounds on log-history reads and client-side caches before they become invisible tax.

# Findings

### [High] The server has no safety net

**Category:**
Testing quality

**Time horizon:**
Immediate

**Blast radius:**
Systemic

**What’s annoying:**
There are no visible tests under `server/api/src`, while the server owns auth, node registration, command queuing, automation evaluation, and log ingestion. The only tests in the repo are frontend-focused, and most of those mock the world into submission.

**Why it matters later:**
This is how regressions survive code review and only show up after someone touches a security boundary or persistence path. The backend is where the expensive bugs live; right now it is basically running without a seatbelt.

**Evidence:**
`glob` found no `server/api/src/**/*.test.ts` files.
Frontend tests like `app/src/dashboard/components/NodeCard.test.ts:109-172`, `app/src/logs/stores/logs.test.ts:29-94`, and `app/src/dashboard/composables/useNodePowerProfile.test.ts:25-31` mostly verify mocked wiring or default state, not server behavior.

**What’s really going on:**
The repo has tests, but not around the parts that would actually hurt if they broke. That creates false confidence: the suite looks alive while the risky paths stay untouched.

**Suggested fix:**
Add a small server integration test slice first: login/logout, register/ingest, command queue, and automation trigger evaluation. Then cover the persistence and authorization branches that have historically been fragile.

**Roast line:**
The backend is carrying critical state with no test harness and a very optimistic attitude.

### [High] Node edits are three separate writes pretending to be one action

**Category:**
Edge-case resilience

**Time horizon:**
Immediate

**Blast radius:**
Feature-level

**What’s annoying:**
The node edit flow submits display name, capability, and order as three independent requests. If the second or third call fails, the form can partially apply server-side while the UI has already moved on.

**Why it matters later:**
Users experience this as flaky saves and weird half-updated nodes. Engineers experience it as one more “can’t repro” bug where the local state, store state, and server state all disagree by a little bit.

**Evidence:**
`app/src/dashboard/composables/useNodeCardEditState.ts:41-75` performs up to three sequential updates and mutates the local `node` after each success.
`app/src/nodes/stores/nodes.ts:47-93` exposes three separate update methods that each replace local state independently.
The server mirrors that split with separate endpoints in `server/api/src/routes/createApiRouter.ts:105-108` and handlers in `server/api/src/controllers/ProvisionController.ts:89-187`.

**What’s really going on:**
The UI models one edit form, but the API models three unrelated mutations. That mismatch is what makes the flow brittle.

**Suggested fix:**
Either introduce one patch endpoint for the node edit form or make the client treat the steps as a transaction-like unit with rollback/error aggregation. Don’t let one screen pretend to be atomic while the network does freestyle.

**Roast line:**
This form has the confidence of a single save button and the implementation of three unrelated PATCH requests.

### [Medium] Log history is rebuilt from scratch on every request

**Category:**
Scalability

**Time horizon:**
3–6 months

**Blast radius:**
Cross-cutting

**What’s annoying:**
`LogArchiveService.list()` loads every recent archive file, parses every entry into memory, filters the whole set, then paginates afterward. Live delivery also walks every listener for every new log entry.

**Why it matters later:**
This is fine when the archive is small and the room is quiet. As log volume rises, each query becomes an archaeology dig, and each new log becomes a linear fan-out event.

**Evidence:**
`server/api/src/services/LogArchiveService.ts:77-96` loads recent days, then filters and paginates in memory.
`server/api/src/services/LogArchiveService.ts:157-162` emits each entry to every subscriber.
`server/api/src/services/LogArchiveService.ts:199-241` reads archives line-by-line and sorts after the fact.

**What’s really going on:**
The archive is acting like a data store, but it is still being queried like a pile of files. That works until the pile stops being cute.

**Suggested fix:**
Move hot log queries into a queryable store or maintain a compact index for recent history. Also add an explicit listener cap or backpressure story before SSE becomes a polite denial-of-service.

**Roast line:**
Every log search is currently a small excavation project.

### [Medium] Power-profile state is cached forever at module scope

**Category:**
Maintainability

**Time horizon:**
3–6 months

**Blast radius:**
Feature-level

**What’s annoying:**
`useNodePowerProfile()` keeps three reactive `Map`s at module scope for state, loading, and error. There is no eviction, no session reset, and no cleanup when the user logs out or nodes disappear.

**Why it matters later:**
That makes stale state sticky and memory growth unbounded across a long-lived app session. It also means the cache survives more than the route that created it, which is a fun way to make debugging feel haunted.

**Evidence:**
`app/src/dashboard/composables/useNodePowerProfile.ts:7-10` defines module-level caches.
`app/src/dashboard/composables/useNodePowerProfile.ts:41-75` only loads on node changes and never clears old entries.
`app/src/dashboard/components/NodeCardActions.vue:23-50` consumes that cache directly from the component path.

**What’s really going on:**
This is global state wearing a composable costume. It works until the app needs to reason about session boundaries, invalidation, or stale records.

**Suggested fix:**
Move the cache into a store with explicit invalidation on logout and node refresh, or bound the cache with a simple eviction rule. The important part is ownership, not cleverness.

**Roast line:**
This cache is a souvenir shop: everything stays forever whether anyone asked for it or not.

### [Medium] Provisioning cleanup depends on the user leaving politely

**Category:**
Edge-case resilience

**Time horizon:**
Immediate

**Blast radius:**
Feature-level

**What’s annoying:**
The BLE provisioning composable creates notify listeners and connection state, but the view never unregisters anything on unmount. The flow has a `reset()` escape hatch, but it only runs on explicit user actions or terminal success/failure.

**Why it matters later:**
If the user navigates away mid-flow, the app can leave a notification listener, timer, or BLE connection hanging around until the process or device state cleans it up for you. That’s how one screen becomes a slow leak.

**Evidence:**
`app/src/composables/useBleProvisioning.ts:57-161` manages `stopStatusNotification` manually and exposes `reset()`, but no lifecycle hook calls it automatically.
`app/src/views/ProvisionView.vue:18-36` sets a timeout watcher, `38-47` opens the pairing window on mount, and `78-83` resets only on an explicit button path.

**What’s really going on:**
The flow relies on manual teardown spread across multiple branches. That is fine when the route completes cleanly, and annoying the first time it doesn’t.

**Suggested fix:**
Call `reset()` from `onBeforeUnmount` or move the full provisioning lifecycle into a composable that owns its own cleanup. Also keep the pairing-window side effect in one place.

**Roast line:**
The provisioning flow trusts the user to exit nicely, which is a bold design choice.

# Systemic Patterns
- The backend has improved its ownership model, but the frontend still likes to split one user intent into several smaller side effects. That pattern shows up in node editing, provisioning, and cached node state.
- The test suite rewards wiring and default values more than failure modes. It gives the shape of confidence without much of the substance.
- Several bits of state are effectively global without being named that way. Module-level caches and manual cleanup are a recurring theme.
- Log and lifecycle behavior are handled locally instead of centrally. That keeps the code easy to start and hard to reason about once the app is running for a while.

# Fix Order
- Fix now: add a small server integration-test harness around the highest-risk API flows. That is the cheapest way to stop future regressions from landing silently.
- Fix now: make node editing behave atomically from the user’s point of view. Partial writes in a single form are where the weird bugs breed.
- Fix now: add unmount cleanup to provisioning and collapse pairing-window side effects into one place.
- Fix next: put bounds or indexing around log-history reads so archive browsing does not become a file-system scavenger hunt.
- Fix next: move `useNodePowerProfile` out of unbounded module caches and into explicit session-owned state.

# What Not To Waste Time On
- Don’t rewrite the NyxKit wrapper layer just because it has a lot of thin methods. The bigger issue is where state and policy live, not the fact that a client SDK exists.
- Don’t chase the `as any` in `HealthPanel.vue` before the actual state and lifecycle issues are fixed.
- Don’t spend energy polishing demo-grade CSS drift while the real risks are still around persistence, tests, and cleanup.

# Final Verdict
This is no longer a chaotic codebase, but it is still a codebase that asks for trust in a few places it hasn’t earned yet. If left alone, it will feel increasingly expensive to change because the hardest bugs will keep hiding in partial updates, stale caches, and untested server paths. Clean up those seams and it can become a solid, maintainable system instead of a nicely organized source of future surprises.
